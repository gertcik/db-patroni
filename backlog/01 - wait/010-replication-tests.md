# Набор тестов для оценки работы репликации

**Статус:** wait
**Приоритет:** high
**Создана:** 2026-08-28
**Дедлайн:** (опционально)

## Описание

Разработать автоматизированный набор тестов для оценки корректности работы репликации на живом кластере Patroni (`patroni-cluster`). Тесты пишутся на **pytest**, оформляются как **docker-контейнер**, запускаемый через `docker compose`, и работают по **уже поднятому кластеру** (не поднимают/сносят стек сами, кроме failover-теста, который останавливает/поднимает мастера). По итогам запуска формируется **HTML-отчёт (pytest + Allure или pytest-html)**, результаты выгружаются в каталог.

Тесты проверяют чтение через **HAProxy R/W :5432** (записи) и **протокольную БД** — **audit-log через pg-audit** (WAL consumer `pg-audit-log`), которая фиксирует типы операций `i` / `d` / `u`.

## Критерии готовности (DoD)

- [ ] Создан отдельный каталог с тестами внутри `patroni-cluster/` (например `patroni-cluster/tests/`)
- [ ] Тесты оформлены как docker-образ + сервис в `docker-compose.yml`, запускаемый одной командой (`docker compose run --rm replication-tests` или аналог)
- [ ] Тесты подключаются к живому кластеру (HAProxy `:5432`, физическая реплика `:5433`, audit-log)
- [ ] Реализован тест 1: INSERT в кластер Patroni → строка появилась на физической реплике и появилась запись типа `i` в протокольной (audit-log) БД
- [ ] Реализован тест 2: DELETE в кластере Patroni → строка удалена с физической реплики и добавлена запись типа `d` в протокольную БД
- [ ] Реализован тест 3: UPDATE в кластере Patroni → строка обновлена на физической реплике и добавлена запись типа `u` в протокольную БД
- [ ] Реализован тест 4 (failover): остановлен лидер → кластер временно недоступен → после восстановления кластер доступен и запросы SELECT проходят
- [ ] По итогам запуска формируется HTML/Allure-отчёт и выгружается в каталог с результатами
- [ ] Команда запуска и каталог результатов задокументированы в README/docs
- [ ] Тесты стабильно проходят на живом кластере (повторяемость)

## Шаги выполнения

1. Создать каталог `patroni-cluster/tests/` (или `tests/` в корне проекта):
   - `requirements.txt` (pytest, psycopg2/psycopg, allure-pytest, pytest-html, requests)
   - `conftest.py` — фикстуры подключения (HAProxy R/W `:5432`, физическая реплика `:5433`, audit-log/pg-audit), функции ожидания/ретраев
   - `test_replication.py` — тесты 1–3 (i/d/u)
   - `test_failover.py` — тест 4 (стойкость лидера)
2. Оформить запуск как docker-контейнер:
   - `Dockerfile` (python + драйверы PG)
   - Сервис `replication-tests` в `docker-compose.yml` (запускается `run --rm`, подключается к сети `patroni-net`)
   - Каталог результатов смонтировать в volume (например `./tests/reports:/reports`)
3. Реализовать тест 1 (INSERT):
   - Вставить запись через HAProxy `:5432`
   - Дождаться появления строки на физической реплике `:5433`
   - Проверить наличие записи типа `i` в протокольной (audit-log) БД
4. Реализовать тест 2 (DELETE):
   - Удалить запись через HAProxy `:5432`
   - Дождаться удаления строки с физической реплики
   - Проверить наличие записи типа `d` в протокольной БД
5. Реализовать тест 3 (UPDATE):
   - Обновить запись через HAProxy `:5432`
   - Дождаться обновления на физической реплике
   - Проверить наличие записи типа `u` в протокольной БД
6. Реализовать тест 4 (failover):
   - Определить текущего лидера (`patronictl list` / REST `:8008`)
   - Остановить лидера (`docker compose stop <master>`)
   - Убедиться, что кластер временно недоступен (записи/чтение не проходят)
   - Дождаться восстановления (новый лидер выбран, HAProxy переключился)
   - Проверить, что SELECT через HAProxy проходит
   - (предусмотреть поднятие бывшего мастера обратно — вернуть/не вернуть по политике теста, задокументировать)
7. Собрать отчёт: запустить pytest с `--alluredir=<reports>/allure` и сгенерировать HTML, либо `--html=<reports>/report.html`
8. Проверить стабильность: прогнать полный набор несколько раз на живом кластере, убедиться в повторяемости
9. Документация: команда запуска, каталог результатов, структура, требования — в `README.md` / `docs/*`
10. Обновить DoD и перенести задачу в `02 - work/` при начале работ, в `03 - done/` после завершения

## Заметки

- Тесты работают по **живому кластеру**: перед запуском предполагается `docker compose up -d`.
- Тест failover (п. 4) — единственный, который влияет на инфраструктуру (останавливает мастера); остальные — read/write через HAProxy с ретраями ожидания репликации.
- Наблюдение за полезной нагрузкой не требуется: для тестов INSERT/DELETE/UPDATE удобно использовать изоляционную таблицу/схему или записи с уникальным префиксом, чтобы не конфликтовать с `load-generator`.
- «Протокольная БД» = **audit-log через pg-audit** (WAL consumer `pg-audit-log`, слот `audit_slot`); типы операций `i`/`d`/`u` берутся из неё.
- Физическая реплика публично доступна на `:5433`; HAProxy R/W мастера — `:5432`.
- Перезапуск/создание тестового контейнера: `docker compose build replication-tests` (или `docker compose run --rm replication-tests pytest ...`).
